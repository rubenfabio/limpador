# T-04.01 — node_modules

**Feature:** F04 · **Fase:** MVP · **Depende de:** T-02.03, T-01.06

## Regras de negócio

- Um item **por projeto**, agrupando todos os `node_modules` do projeto (raiz e pacotes de monorepo). O detalhe lista as pastas.
- `node_modules` dentro de outro `node_modules` não é item separado.
- Risco 🟡, natureza recriável, exclusão direta.
- **Como recriar**, pelo arquivo de lock: `pnpm-lock.yaml` → `pnpm install`; `yarn.lock` → `yarn install`; `package-lock.json` → `npm ci`; `bun.lock`/`bun.lockb` → `bun install`.
- **Sem arquivo de lock**: continua 🟡, com o alerta "reinstalar pode trazer versões diferentes".
- **Tamanho liberável**: arquivos com hardlink compartilhado (comum no pnpm) não contam, porque não liberam espaço. O detalhe mostra o tamanho aparente e o liberável.
- **Junções e links** nunca são seguidos: remover o link, nunca o destino (I3).
- Projetos ativos aparecem com peso reduzido (T-01.03).
- Se houver processo usando arquivos da pasta (servidor de desenvolvimento rodando), o item é ⛔.

## Critérios de aceite

- [x] **CA1** Dado um monorepo com 3 `node_modules`, quando analisado, então gera 1 item com as 3 pastas no detalhe.
- [x] **CA2** Dado um projeto com `pnpm-lock.yaml`, quando analisado, então "como recriar" é `pnpm install`.
- [x] **CA3** Dado um `node_modules` de pnpm em que todos os arquivos são hardlinks do store, quando analisado, então o tamanho liberável é muito menor que o aparente.
- [x] **CA4** Dada uma junção dentro de `node_modules` apontando para fora, quando a pasta é removida, então o destino da junção continua intacto.
- [x] **CA5** Dado um projeto sem lock, quando analisado, então o item tem o alerta de versões diferentes.
- [x] **CA6** Dado um arquivo de `node_modules` aberto por outro processo, quando revalidado, então o item fica ⛔.
