# T-09.04 — Entrada na quarentena

**Feature:** F09 · **Fase:** MVP · **Depende de:** T-01.04

## Regras de negócio

**Como cada tipo entra**

| Tipo | Como fica guardado |
|---|---|
| Pasta ou arquivo (worktree, transcrição, Downloads, ambiente virtual) | Movido para a área de quarentena **no mesmo disco**, preservando a estrutura e as datas |
| Branch | Referência preservada (protegida da coleta de lixo do git) + configuração de upstream |
| Stash | Referência preservada + patch exportado |
| Volume Docker | Conteúdo exportado para arquivo + metadados (nome, rótulos, driver) |
| Container com dados | Snapshot da camada gravável + configuração |

- Se não for possível mover no mesmo disco, o app copia, verifica e só então apaga o original. Isso exige espaço livre; sem espaço, a ação é bloqueada com mensagem.
- **Verificação de integridade antes de remover o original**: contagem e tamanho dos arquivos (pastas), existência da referência (git), leitura do arquivo exportado (volumes).
- **Registro na quarentena**: identificador, cópia completa do item original (todos os campos), origem (manual, automática ou agente), data de entrada, data de expiração (entrada + prazo vigente), espaço ocupado, local e instruções de restauração.
- O prazo usado é o que estava vigente no momento da entrada.

## Critérios de aceite

- [ ] **CA1** Dada uma pasta movida para a quarentena, quando verificada, então tem os mesmos arquivos, tamanhos e datas.
- [ ] **CA2** Dada uma falha na verificação de integridade, quando detectada, então o original **não** é removido e o item termina como "falhou".
- [ ] **CA3** Dado um item na quarentena, então o registro tem a data de expiração igual à entrada + 14 dias (padrão).
- [ ] **CA4** Dado um disco sem espaço para copiar entre discos, quando a ação é pedida, então é bloqueada com mensagem.
